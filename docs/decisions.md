# Решения и почему

| # | Решение | Почему |
|---|---|---|
| 1 | Python + FastAPI | один язык для сервера и тестов; встроенная документация API на `/docs` |
| 2 | SQLite через SQLAlchemy | база в одном файле, не нужно ставить сервер БД; данные переживают перезапуск |
| 3 | Интерфейс — одна HTML-страница с небольшим JavaScript, без сборщика | меньше частей — проще запустить и объяснить |
| 4 | Логика в `services.py`, маршруты в `main.py` только вызывают её | логику можно проверить тестами без HTTP и объяснить отдельно |
| 5 | Время хранится в UTC | нет путаницы с часовыми поясами; показываем в местном времени на странице |
| 6 | Свой тип колонки `UTCDateTime` | SQLite не хранит часовой пояс; без перевода в UTC отчёт сдвигается (найдено тестом, см. `ai-log.md`) |
| 7 | Время без часового пояса — ошибка, а не «угадывание» | «12:00» без пояса неоднозначно; лучше упасть сразу, чем исказить отчёт |
| 8 | Частичный уникальный индекс: один активный таймер на сотрудника | защита в самой базе — даже если два запроса «старт» придут одновременно, второй не пройдёт |
| 9 | `PRAGMA foreign_keys=ON` на каждом соединении | SQLite по умолчанию не проверяет внешние ключи; проверено: без него запись для несуществующего сотрудника проходит |
| 10 | Имена сотрудников не уникальны | в компании бывают тёзки; различаем по id |
| 11 | Текущее время — зависимость `get_now`, а не вызов внутри логики | тесты «двигают часы» и проверяют длительность точно, без ожидания |
| 12 | Отчёт за период [начало, конец): считается только часть записи внутри периода | работа 23:00–01:00 честно делится между днями |
| 13 | Идущий таймер в отчёте — до текущего момента, с пометкой «идёт» | иначе отчёт врёт о работающем сотруднике |
| 14 | Сотрудники без записей показываются в отчёте с нулём; пустой отчёт — не ошибка | так видно, что человек есть, но не работал |
| 15 | Период приходит с часовым поясом; страница считает «сутки» по местному времени | «отчёт за 7 ноября» значит местные сутки, а не сутки по UTC |
| 16 | Часы на странице считаются от данных сервера («прошло N секунд»), а не от часов компьютера | если часы на компьютере сбиты, таймер всё равно показывает верно |
| 17 | Весь пользовательский текст на странице — через `textContent` | имя с HTML-тегами показывается буквами и не выполняется (проверено в браузере) |
| 18 | Перерыв и обед — те же записи времени, с типом `kind` | одна таблица, одно правило «один идущий таймер»; отчёт делит время по типам |
| 19 | «Перерыв», «Обед», «Вернуться к работе» — одно действие (`/timer/switch`) | между записями нет разрыва во времени, сотрудник жмёт одну кнопку |
| 20 | При возврате к работе продолжается последняя задача | не надо заново вписывать то, чем занимался до обеда |
| 21 | В отчёте `total_seconds` — только работа; перерывы и обед — отдельными полями | бухгалтерии нужно рабочее время без перерывов; старые клиенты API не ломаются |
| 22 | Мини-миграция в `init_db`: добавить колонку `kind`, если её нет | `create_all` не меняет существующие таблицы; проверено на копии настоящей базы владельца |
| 23 | Большие часы — «отработано сегодня», а не текущий отрезок | сотруднику важна сумма за день; на перерыве часы стоят, у перерыва свои |
| 24 | Начало «сегодня» присылает страница (местная полночь) | сервер не знает пояс пользователя; без параметра — полночь UTC |
| 25 | Один подсчёт `_seconds_by_kind` для отчёта и для дня | одно правило в одном месте — не разъедутся |
