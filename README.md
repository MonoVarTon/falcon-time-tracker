# Учёт рабочего времени

Веб-приложение для учёта рабочего времени сотрудников — тестовое задание на вакансию «Программист» в Falcon AI.

Сделано под реальную среду клиентов Falcon AI — **диспетчерскую грузоперевозок в США**: демо-данные — диспетчеры, безопасность, биллинг и рекрутер водителей, а сутки считаются по часам офиса (по умолчанию Чикаго), даже если сотрудник работает удалённо из другой страны.

| Что требует задание | Где сделано |
|---|---|
| Добавление сотрудников | форма «Добавить сотрудника» · `POST /api/employees` |
| Запуск и остановка таймера с описанием задачи | «Начать работу» / «Закончить» · `…/timer/start`, `…/timer/stop` |
| Записи и общее время каждого сотрудника за период | «Отчёт за период» · `GET /api/report` |
| Сохранение данных после перезапуска | SQLite-файл; проверено тестами `test_employee_survives_restart`, `test_data_survives_app_restart` |
| Проверки: повторный запуск таймера, пустой отчёт | `test_second_start_is_rejected`, `test_empty_report`, `test_empty_report_without_employees` |

## Запуск

Нужен Python 3.10 или новее (проверено на Windows с Python 3.12 и на Linux с Python 3.10).

```
git clone https://github.com/MonoVarTon/falcon-time-tracker.git
```

**Windows (командная строка):**
```
cd falcon-time-tracker
python -m venv .venv
.venv\Scripts\activate
python -m pip install -r requirements.txt
python -m uvicorn app.main:app
```

**macOS / Linux:**
```
cd falcon-time-tracker
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m uvicorn app.main:app
```

Откройте **http://localhost:8000**. Документация API — **http://localhost:8000/docs**.

Отдельное окружение `.venv` нужно, чтобы версии библиотек проекта не меняли общий Python на компьютере.

### Демо-данные одной командой

Вымышленная диспетчерская: 5 сотрудников и неделя их работы с перерывами и обедами. Удобно смотреть на отдельной базе, не трогая рабочую:

```
set DATABASE_URL=sqlite:///./demo.db        (Windows)
export DATABASE_URL=sqlite:///./demo.db     (macOS / Linux)
python -m app.seed
python -m uvicorn app.main:app
```

В базу, где уже есть сотрудники, команда писать отказывается — демо не смешивается с настоящими данными (добавить всё равно: `python -m app.seed --append`).

«Сегодня» в демо строится от текущего момента по часам компании. Если в Чикаго ночь, диспетчеры в демо работают ночную смену — для диспетчерских это нормально.

В демо специально есть сотрудник с **забытым таймером**: он сразу виден наверху списка с пометкой «Требуют внимания».

| Переменная | По умолчанию | Что задаёт |
|---|---|---|
| `DATABASE_URL` | `sqlite:///./timetracker.db` | файл базы |

## Что умеет

**Сотрудник:** «Начать работу» с задачей → «Перерыв» / «Обед» → «Вернуться к работе» (прежняя задача продолжается) → «Закончить». Большие часы показывают **«отработано сегодня»** — сумму работы за день; на перерыве они стоят, у перерыва свои часы.

**Руководитель:**
- фильтры в шапке: все / требуют внимания / работают / на паузе / не начали; поиск по имени;
- **«Требуют внимания» — первыми в списке:** таймер идёт больше 10 часов или остановился сам;
- **забытый таймер останавливается сам через 12 часов** — ровно на отметке «начало + 12 ч», с пометкой «уточните время»;
- **продление рабочего дня** (+2/+4/+6 ч, не больше 24) с именем подтвердившего руководителя;
- **исправление времени окончания с подсказкой:** «обычно уходит в 17:10 — среднее по 4 дням»; исправленная запись помечена «✎ исправлено» с причиной — в отчёте видно, какие часы точные, а какие восстановлены.

**Отчёт за период:** время работы каждого сотрудника, отдельно перерывы и обед, список записей и **лента дня** — полосы работы, перерывов и обеда на общей шкале часов. Работа через полночь честно делится между днями.

## Как устроено

```
app/
  config.py    часовой пояс компании и границы суток
  db.py        подключение к SQLite и обновление старой базы
  models.py    таблицы: сотрудники и записи времени
  schemas.py   что API принимает и отдаёт (проверка ввода)
  services.py  все правила: таймер, перерывы, отчёт, автоостановка, исправление
  main.py      адреса API — тонкие: принять запрос → вызвать правило → ответить
  seed.py      демо-данные
static/
  index.html   страница: HTML, CSS и JavaScript без сборщика
  timeline.js  расчёт ленты дня (чистые функции, покрыты тестами)
tests/         112 проверок pytest; одна из них запускает 10 проверок JavaScript
docs/
  decisions.md все решения с объяснением «почему»
  ai-log.md    журнал ошибок ИИ: что пошло не так, как нашли, как исправили
```

Главные решения (полный список с причинами — в [`docs/decisions.md`](docs/decisions.md)):

- **Таймер идёт, пока у записи пустое время окончания.** Отдельного флага нет — данным нечем противоречить себе.
- **Один идущий таймер на сотрудника** охраняется дважды: правилом в коде (понятная ошибка 409) и частичным уникальным индексом в базе — на случай двух одновременных нажатий.
- **Всё время хранится в UTC.** SQLite не хранит часовой пояс, поэтому есть свой тип колонки `UTCDateTime`; время без пояса отклоняется.
- **Сутки — по часам компании.** Удалённый диспетчер работает по американским часам; его смена 17:00–02:00 по Чикаго — один рабочий день компании. В день перевода часов сутки длятся 23 или 25 часов, и это учтено.
- **Текущее время — зависимость `get_now`.** Тесты «двигают часы» и проверяют длительность точно, без ожидания.
- **Обновление базы без потерь:** новые колонки добавляются в старую базу при запуске (`ADDED_COLUMNS` в `db.py`). Проверено на настоящей базе, созданной первой версией.
- **Вывод на странице только через `textContent`** — имя с HTML-тегами показывается буквами и не выполняется.

## Тесты

```
python -m pytest -q
```

Проверки покрывают все функции задания и граничные случаи: повторный запуск, пустой отчёт, работу через полночь, день перевода часов, перерывы, автоостановку, продление, исправление, перезапуск приложения, обновление старой базы. Тесты работают на временной базе и никогда не трогают рабочую.

Тесты проверялись «на прочность»: в код нарочно вносилась ошибка и смотрелось, ловит ли её хоть одна проверка. Дважды не поймала — и именно так были найдены недостающие проверки (см. журнал ниже).

Проверки ленты дня написаны на JavaScript и запускаются из pytest, если установлен Node.js; без него они пропускаются.

### Примеры запросов

Реальные запросы из работы над проектом (с сохранением смысла):

1. Постановка: «Сначала посмотри мои наработки: что можно взять за основу — стек, похожие приложения. Потом предложи каркас и план, к коду — после моего „поехали“. Код должен быть понятен мне: каждое решение поясняй».
2. Ошибка, найденная руками: «Когда нажимаешь обед или перерыв, рабочее время на таймере сбрасывается, а не продолжается. В отчёте, может, и учитывается, но сотрудник сам не видит, сколько он работает в сумме». → большие часы стали «отработано сегодня».
3. Продуктовая идея: «Нужно автоматическое отключение таймера на 12 часах, а если сотрудник задерживается сверхурочно — подтверждение от начальника. И исправление с подсказкой: за последние 7 дней уходил во столько-то — значит, среднее и ставим». → автоостановка, продление, подсказка.
4. Привязка к заказчику: «Посмотри ещё раз ссылку и пойми, что за компания Falcon: где находится, чем занимается». → разбор компании, демо «диспетчерская», часовой пояс офиса.
5. Масштаб: «Чтобы такие люди выпадали в списке сверху — если вдруг там будут сотни сотрудников». → «Требуют внимания» и фильтры.
6. Удержание рамок: «А мы сейчас в лес не уйдём от задания? Может, вернуть к более простой форме, а в README описать схему работы?» → заморозка функций, развитие описано ниже.

## Найденные и исправленные ошибки

Все случаи — реальные; полный журнал — [`docs/ai-log.md`](docs/ai-log.md). Самые показательные:

| Что ИИ сделал не так | Как нашли | Как исправили |
|---|---|---|
| Записал время стандартным `DateTime(timezone=True)`. SQLite не хранит пояс: «12:00 по Минску» вернулось как «12:00» без пояса — отчёты тихо съехали бы на 3 часа | тест сохранил и перечитал время | свой тип `UTCDateTime`; время без пояса — ошибка |
| В комментарии внутри скрипта страницы был текст `</script>` — браузер счёл его концом скрипта, кнопки молча не работали | тесты API были зелёные; поймал только прогон в настоящем браузере | комментарий переписан, добавлен тест на целостность скрипта |
| Большие часы показывали текущий отрезок и обнулялись после обеда | **нашёл человек** при ручной проверке — тесты проверяли расчёт, а не смысл экрана | часы «отработано сегодня» |
| Собственная проверка ИИ требовала «в папке нет файла базы» — и упала на настоящей базе владельца; удаление «по совету теста» уничтожило бы данные | перед удалением посмотрел, что в файле | проверка переписана; база не тронута (sha256 до и после совпали) |
| Тесты незаметно создавали рабочую базу при запуске приложения | увидел файл после ручного запуска, воспроизвёл | тесты задают временную базу до импорта приложения + отдельная проверка |
| Подсказка «обычно уходит в 17:00» считалась как «полночь + минуты»: в день перевода часов (сутки 25 ч) вышло бы 16:00 | нарочно сломал расчёт — **ни один тест не упал** | время «как на стене»; добавлен тест именно на 1 ноября |
| Цвет «перерыва» выбран на глаз и почти сливался с «работой», в том числе для людей с нарушением цветовосприятия | валидатор палитры до отрисовки | цвет заменён, все проверки различимости пройдены |
| После исправления последнего «требующего внимания» фильтр оставался включён на пустом списке — без выхода | прогон сценария в браузере | возврат ко «Все» до отрисовки |
| Подсказка времени ухода падала с ошибкой 500 при уходе в 23:59:45 и не работала для ночных смен 17:00–02:00 | **ревью второй моделью** (Gemini 3.8 Flash) | подсказка считается по сменам, уход — от дня начала смены |
| Проверка пояса Минска проходила, даже если пояс игнорировать (15:00 UTC = 18:00 Минск — совпадает) | **ревью второй моделью** | проверка смотрит и на местное время в объяснении |

Вывод из журнала: зелёные тесты — не доказательство. Половину ошибок поймали не тесты, а прогон в браузере, ручная проверка человеком, нарочная поломка кода и **вторая модель**.

### Независимое ревью второй моделью

Gemini 3.8 Flash прочитал код без доступа к правке и нашёл 10 замечаний. Каждое проверено воспроизведением:

| | Итог |
|---|---|
| Подтверждены и исправлены (с проверкой, падавшей на старом коде) | 6: падение подсказки около полуночи, ночные смены, «пустая» проверка пояса, потерянное продление, неограниченный период отчёта, устаревшая документация |
| Исправлены как мелочь | 2: отметка «сейчас» по часам сервера; защита формы продления на пределе 24 ч (на практике недостижимо) |
| Оставлены сознательно | 2: режим WAL для SQLite (ожидание блокировки в Python по умолчанию 5 секунд, а не 0, как писал ревьюер) и пакетная загрузка списка сотрудников — описаны в «Как развивать» |
| Уточнены | гонка продлений не превышает 24 ч, как утверждалось, — настоящая беда в том, что второе подтверждение молча затирало первое |

Ревью нашло две ошибки, которые пропустили и тесты, и проверки на прочность. А проверка исправлений нашла ещё две — в собственном коде и тесте Claude.

## Ограничения (сознательно)

- **Нет входа и ролей** — задание прямо их исключает. Поэтому «подтверждение руководителя» при продлении — это записанное имя, а не проверка роли, а исправлять время может любой, кто открыл страницу. Причина исправления сохраняется — видно, кто и почему поправил.
- **Один часовой пояс на компанию.** Схема для сотрудников в разных поясах — ниже.
- **Фильтры и поиск работают на странице** — мгновенно, но рассчитаны на сотни сотрудников, не на десятки тысяч.
- **Часы водителей не учитываются.** У водителей грузовиков в США свои федеральные правила о часах работы и электронные журналы (Hours of Service, ELD) — это отдельный регулируемый мир. Приложение — для офиса диспетчерской; залезть в водительский учёт наполовину хуже, чем не залезать.

## Как развивать

1. **Сутки по поясу каждого сотрудника, показ — по часам смотрящего.** Отработанное время от поясов не зависит (всё хранится в UTC); пояс влияет только на то, где кончается «понедельник». Если считать сутки по часам того, кто смотрит, руководитель в Чикаго и бухгалтер в Нью-Йорке увидят за одну дату разные цифры. Правильно: пояс — в карточке сотрудника (заполняется с его браузера), его сутки — по его поясу, а время на экране — по часам смотрящего. Расчёт суток уже вынесен в одну функцию (`company_day_bounds`), меняется только источник пояса.
2. **Вход и роли:** сотрудник видит себя, руководитель — свою команду и подтверждает продления, бухгалтер — отчёты.
3. **Сверхурочные:** пометка недели больше 40 часов — основа расчёта оплаты сверхурочных в США.
4. **Выгрузка:** таблица CSV для бухгалтерии и табель недели для подписи сотрудника и руководителя (PDF).
5. **ИИ-бухгалтер:** в конце периода сам собирает часы, проверяет аномалии (забытые и неисправленные таймеры, дни без обеда, резкий рост часов), пишет пояснение и проводит табель по подписям: сотрудник → руководитель → бухгалтер. Деньги и налоги считает обычный код по правилам, а не модель; последняя подпись — за человеком.
6. **Пропуска и турникет:** проходы по карте — это факт, а не догадка. Время входа и выхода от турникета подсказывает начало и конец дня и закрывает проблему «забыл нажать». Риски: присутствие — не работа, «прошёл за коллегой», персональные данные.
7. **Связь с системами компании:** TMS и HR-бот Falcon AI — сотрудник заводится один раз, табель уходит туда, где по нему платят.
8. **Масштаб:** PostgreSQL вместо SQLite (или режим WAL, если остаётся SQLite), поиск и постраничный вывод на сервере, загрузка состояния всех сотрудников одним запросом вместо двух на каждого.
9. **Зависимости:** Starlette предупреждает, что тестовый клиент переезжает с `httpx` на `httpx2` — обновить при следующем обновлении FastAPI.
